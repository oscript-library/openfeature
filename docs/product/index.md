# Продуктовое описание `openfeature`

## Задача

Фича-флаг начинается с одного `Если` и переменной окружения. Потом появляется второй флаг, потом нужно включить
возможность только для части пользователей, потом выясняется, что флаги читаются в десяти местах по-разному, а выключить
их на проде можно только перезапуском. Когда команда решает купить систему управления флагами, оказывается, что её SDK
проник в прикладной код целиком.

OpenFeature - открытая спецификация API оценки флагов под эгидой CNCF. Прикладной код работает с клиентом, а
конкретная система управления флагами подключается провайдером. Сменить систему означает заменить одну строку
регистрации провайдера.

Библиотека решает три задачи:

* дать прикладному коду единый API оценки флагов четырёх типов;
* гарантировать, что флаги не роняют приложение: любая внештатная ситуация даёт значение по умолчанию;
* дать точку расширения для метрик, аудита и обогащения контекста через хуки.

## Кому пригодится

| Ситуация | Что даёт библиотека |
|---|---|
| Возможность выкатывается частями | Флаг вместо ветки в системе контроля версий |
| Тёмный запуск и постепенная выкатка | Правила таргетинга по атрибутам контекста |
| Аварийное выключение возможности | `JsonFileProvider` с перечитыванием: правка файла вместо перезапуска |
| Тесты с разными наборами флагов | `InMemoryProvider` и изолированные экземпляры API |
| Планируется переход на систему управления флагами | Прикладной код не изменится, поменяется только провайдер |
| Нужен учёт того, какие флаги читаются | Хук уровня API вместо правок в местах вызова |

## Отличия от альтернатив

**Переменные окружения.** Работают, пока флагов немного и значение одно для всех. Не дают таргетинга, не меняются без
перезапуска и ничего не сообщают о том, почему получено именно это значение.

**Свой модуль флагов.** Появляется в каждом проекте и в каждом свой: разные имена методов, разное поведение
при отсутствии флага, разные способы задать значение по умолчанию. OpenFeature фиксирует контракт, знакомый
разработчикам из других экосистем, и заранее отвечает на вопросы про типы, причины и коды ошибок.

**SDK конкретного вендора.** Быстрый старт и полная привязка: имена методов, формат контекста и способ инициализации
приходят от вендора. При переезде меняется каждое место чтения флага. Здесь вендор живёт за границей провайдера.

**Прямое чтение конфигурационного файла.** Не хватает главного: поведения при испорченном файле, значений по умолчанию,
таргетинга и внятной причины отказа. `JsonFileProvider` закрывает это, оставляя тот же прикладной API.

## Спецификация

Реализованы обязательные требования разделов
[Flag Evaluation](https://openfeature.dev/specification/sections/flag-evaluation),
[Providers](https://openfeature.dev/specification/sections/providers),
[Evaluation Context](https://openfeature.dev/specification/sections/evaluation-context) и
[Hooks](https://openfeature.dev/specification/sections/hooks):

* API - глобальный синглтон; есть и фабрика изолированных экземпляров (раздел 1.8);
* регистрация провайдера вызывает `Инициализировать` у нового и `Завершить` у предыдущего;
* до регистрации провайдера работает заглушка, возвращающая значения по умолчанию с причиной `DEFAULT`;
* клиент не выбрасывает исключений и гарантирует тип: значение неожиданного типа заменяется значением по умолчанию
  с кодом `TYPE_MISMATCH`;
* `EvaluationDetails` содержит ключ флага, значение, вариант, причину, код и сообщение об ошибке; поле метаданных
  при отсутствии данных - пустая запись, а не `Неопределено`;
* причины и коды ошибок соответствуют перечням спецификации;
* порядок стадий хуков и слияние контекстов - по спецификации; ошибка в хуке приводит к штатному отказу оценки.

## Ограничения

| Ограничение | Комментарий |
|---|---|
| События провайдера не реализованы | `PROVIDER_READY`, `PROVIDER_CONFIGURATION_CHANGED` и прочие |
| Транзакционный контекст не реализован | Контекст задаётся уровнем приложения и уровнем вызова |
| Доменные провайдеры не поддержаны | `ПолучитьКлиента("домен")` возвращает клиент с метаданными домена, но отдельный провайдер к домену не привязывается |
| Tracking API не реализован | Учёт целевых событий остаётся за приложением |
| Правила таргетинга простые | `InMemoryProvider` умеет «значение атрибута входит в список»; сложная логика - дело провайдера |
| Процентная выкатка не встроена | Причина `SPLIT` предусмотрена, распределение реализует провайдер |
| Готовых провайдеров для внешних систем нет | В поставке `InMemoryProvider`, `JsonFileProvider`, `NoopProvider` |

Провайдер для внешней системы пишется по контракту из восьми методов, см.
[`ResolutionDetails`](../api/Классы/ResolutionDetails.md#свой-провайдер).

## Решения

**Клиент молчит об ошибках, но не скрывает их.** Методы оценки не выбрасывают исключений, потому что флаг не повод
ронять запрос. Причина отказа при этом не теряется: она в `КодОшибки` и `СообщениеОбОшибке` у методов с деталями.

**Провайдер, не сумевший подняться, не мешает старту.** Исключение при `Инициализировать` перехватывается: провайдер
сообщит о проблеме своим состоянием, а приложение поднимется на значениях по умолчанию.

**Проверка типа на стороне клиента.** Провайдер может вернуть значение неожиданного типа, например если в JSON строку
записали вместо числа. Спецификация требует в этом случае отдать значение по умолчанию, а не приводить типы молча.

**Состав методов хука определяется рефлексией и кэшируется.** Разбор состава методов заметно дороже самой оценки
флага, поэтому результат запоминается по типу объекта.
